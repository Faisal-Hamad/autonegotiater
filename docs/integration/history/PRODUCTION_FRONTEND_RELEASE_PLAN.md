# Production Frontend Release Plan — 2026-10-19

## النطاق وحالة القرار

هذه إضافة جديدة إلى سجل التدقيق السابق، ولا تستبدل تقاريره أو نتائجه التاريخية. المطلوب إصدار واجهة إنتاج حقيقية مع تعطيل Mock، وليس نشر حاوية Demo. القرار الحالي: **NO-GO للنشر** حتى تنفيذ بوابات التحقق أدناه والحصول على موافقة نهائية مستقلة. لم يتم تعديل مصدر التطبيق أو إعدادات الإنتاج أثناء هذا الفحص.

الإصدار الأول المقترح يعرض التصميم المعتمد مع حالات Integration in Progress للوظائف غير المتكاملة. لا يعرض بيانات تجريبية كبيانات حقيقية، ولا يضمن إتاحة الوظائف التشغيلية الحالية أثناء انتظار تكامل الفريق الخلفي. تبقى السجلات والاتفاقيات في قاعدة البيانات دون تعديل، لكن عرضها عبر الواجهة الجديدة ينتظر صلاحيات وعقود API موثقة. يلزم قبول هذا الأثر الوظيفي قبل الاستبدال.

## العوائق والمخاطر

1. **P0: تراجع إصدار الإطار.** المحلي يثبت Next.js 15.5.4 والإنتاج 15.5.27. لا يُنشر البناء المحلي الحالي. خطة التعديل تتضمن محاذاة package.json وlockfile إلى النسخة المتحققة 15.5.27 مع مراجعة النشرات وقت التنفيذ، ثم إعادة الاختبارات. توجد إصلاحات رسمية أحدث من 15.5.4؛ نجاح البناء لا يعالج هذا العائق. المصادر: https://nextjs.org/blog/security-update-2025-12-11 وhttps://nextjs.org/blog/CVE-2025-66478 . لم تُجر اختبارات استغلال.
2. **P0: النشر التلقائي.** workflow Deploy نشط عند push إلى main وكذلك manual dispatch. يتضمن SSH وgit reset --hard على الخادم وعمليات compose وإعادة تشغيل Nginx وتنظيف صور. لذلك لا يُستخدم push إلى main كوسيلة إصدار الآن، حتى لو كانت الملفات وثائق فقط. قد يطمس تعديلات الخادم أو يمس خدمات أخرى. يجب ضبط مسار النشر بمعرفة المالك قبل أي نشر كود لاحق.
3. GitHub webhooks لم يمكن التحقق منها (401): **NOT_VERIFIED**. وجود workflow معروف لا ينفي أتمتة خارجية. مؤقت deploy الذي فُحص يشغّل Podman healthcheck، وليس دليل نشر تلقائي؛ cron وأتمتة خارجية أخرى **NOT_VERIFIED**.
4. صلاحيات Backend الفعلية وملفات تعريف الارتباط ومسارات تسجيل الدخول لم تُختبر. غياب middleware من manifest الواجهة لا يثبت غياب حماية Backend. الواجهة الجديدة تفشل مغلقة للبيانات الخاصة، ولا يُعد اختيار الدور تفويضًا.
5. صورة Demo تُفعّل Mock أثناء البناء؛ USE_MOCK_DATA=false وقت التشغيل لا يحولها إلى إصدار حقيقي. يحظر نشرها أو إعادة تسمية صورتها لهذا الغرض.
6. مصدر الصفحة الرئيسية القديمة يتضمن مسار تهيئة قد يكتب بيانات؛ لا يُستدعى bootstrap أثناء التحقق أو في الإصدار الجديد.
7. ملف Nginx مربوط كملف منفرد: استبداله بعملية rename قد يترك الحاوية مرتبطة بالـinode القديم. التغيير والتراجع بعد الموافقة يجب أن يحافظا على الربط ويتحققا من hash داخل الحاوية والمضيف.

## خطة البناء وStaging المعزول — لم تنفذ بعد

1. تنفيذ تعديلات frontend أعلاه بعد الموافقة، ثم اختبارات Mock والإنتاج وTypeScript والبناء.
2. بناء صورة جديدة باسم localhost/autoneg-frontend-web:20261019-r1 مع AUTONEG_ISOLATED_DEMO_BUILD=false وUSE_MOCK_DATA=false أثناء البناء والتشغيل. لا نسخ .env أو مفاتيح أو أسرار. npm ci بملف القفل المصحح؛ حزم التطوير متاحة لمرحلة البناء.
3. بيئة Linux/Podman معزولة، حاوية جديدة autoneg-nextjs-web-r1-stage، ربط 127.0.0.1:33127:3000 فقط. لا اتصال بشبكة الإنتاج، API غير متاح (loopback:9)، ولا Mounts لخدمات الإنتاج. لا تغيير staging-r1 أو demo-r1.
4. /health/frontend يعيد mode=production وmock=false ومعرف الإصدار والقدرات فقط، دون أسرار أو فحص DB، مع no-store. لا استخدام /api/health لفحص الواجهة عبر النطاق لأن Nginx يوجه /api إلى FastAPI.
5. اختبارات متصفح لكل الأدوار والمنتجات والروابط المباشرة والجوال، منع استعادة localStorage التجريبي، غياب البيانات الوهمية والتنزيلات المزيفة، منع الطلبات الخاصة وbootstrap، وعدم تسرب حدود الأسعار، وحالات 401/403/عدم توفر الشبكة باستخدام fixtures معزولة.
6. توثيق صورة الاختبار بالـImage ID وdigest وSHA-256 الأرشيف. المرشح النهائي يجب أن يكون نفس الصورة المختبرة؛ لا إعادة بناء صامتة بعد الاختبار. لا يكفي نجاح بناء Windows لإثبات تشغيل حاوية Linux.

## النسخة الاحتياطية والتراجع — خطة وليست نسخة منجزة

الحالة الحالية: **BACKUP_NOT_CREATED / RESTORE_NOT_REHEARSED**. التفويض الحالي لفحص AWS للقراءة فقط، فلا يجوز الادعاء بتجربة التراجع أو إنشاء ملفات خادم.

بعد موافقة مستقلة على هذه العمليات:

- حفظ صورة الواجهة الحالية بصيغة OCI في مسار نسخة احتياطية خاص ومؤرخ مع checksum، دون prune أو حذف الصور والحاويات.
- حفظ نسخة مطابقة بايتًا لملف Nginx وبصمته وصلاحياته، وتوثيق IDs وأوقات بدء الخدمات. لا نسخ .env أو TLS keys أو raw inspect أو بيانات قاعدة البيانات.
- إبقاء autoneg-nextjs-secure يعمل كهدف تراجع فوري؛ لا حاجة لإعادة بناء بيئته السرية عند إعادة التوجيه إليه. إعادة الإنشاء الكاملة في كارثة تحتاج لاحقًا مسارًا معتمدًا لإدارة الأسرار؛ هذا لم يُتحقق منه.
- اختبار تحميل أرشيف الصورة وتشغيله معزولًا دون شبكة إنتاج أو bootstrap، والتحقق من بنائه/أصوله دون قراءة DB. مطابقة checksum وحدها ليست اختبار تراجع وظيفيًا. إن احتاج التشغيل أسرارًا أو اتصال DB، يسجل الاختبار غير مكتمل ولا يُستبدل الإنتاج دون معالجة.
- إجراء rehearsal لاستعادة إعداد التوجيه في بيئة Nginx معزولة؛ توثيق النتيجة قبل الموافقة على القطع.

## القطع المستقبلي للواجهة فقط — مشروط بالموافقة النهائية

1. إعادة فحص hash الإعداد والصور والمنفذ والأتمتة؛ أي اختلاف عن الدليل يتطلب تحديث الخطة.
2. إنشاء مرشح منفصل autoneg-nextjs-web-r1 من نفس صورة Staging المختبرة، alias=nextjs-web-r1 على autonegotiater_default، دون منفذ عام. الكتالوج والميزات الخاصة معطلة؛ لا وصول DB.
3. فحص صحة المرشح دون لمس API الإنتاج أو bootstrap.
4. تغيير سطر واحد فقط في ملف Nginx: `proxy_pass http://nextjs-secure:3000;` إلى `proxy_pass http://nextjs-web-r1:3000;`. حساب الاستبدال محليًا في الذاكرة وجد تطابقًا واحدًا. SHA المتوقع للملف إذا بقيت البقية كما هي: `7df50fd386a3178a73b28d0aa74c3c2c0a21fae25d37dab5252fec08099871a5`.
5. حفظ inode/صلاحيات وربط الملف: كتابة مضبوطة في نفس الملف بعد حفظ النسخة وشرط baseline hash؛ التحقق من hash المضيف والحاوية. لا تغيير /api أو/media أوTLS أوheaders أوauth.
6. nginx -t، ثم graceful reload فقط عند النجاح وبموافقة النشر. لا restart ولا podman-compose ولا git reset/pull ولا image prune.
7. تحقق /health/frontend والأصول والتنقل والحالات الفارغة، ثم إعادة مقارنة IDs وأوقات بدء FastAPI/PostgreSQL/Redis/Celery وأنها لم تتغير. مراقبة محدودة دون طباعة أسرار أو سجلات خاصة.

### التراجع

عند فشل صحة الواجهة أو الأصول أو الصلاحيات: استعادة بايتات ملف Nginx المحفوظ **داخل نفس الملف**، التأكد من SHA القديم على المضيف والحاوية، nginx -t ثم graceful reload؛ يعود التوجيه إلى nextjs-secure العامل. التحقق من رجوع الواجهة والخدمات الأساسية دون استعادة DB أو migrations. لا تحذف المرشح أو النسخ الاحتياطية أثناء المعالجة. إن فشل اختبار Nginx لا reload؛ أعد الملف المعروف أولًا. تغيّر baseline أو فقدان الهدف القديم يوقف القطع.

## نتائج التحقق المحلي المتاحة

- PASS: تسع مجموعات verify-*.cjs، بما فيها 114 محاكاة تنافسية على 7 منتجات و424 tick، ملكية البائع، التقارير، اللغة الإنجليزية وعزل Demo والتكامل.
- PASS: بناء Next.js الطبيعي مع AUTONEG_ISOLATED_DEMO_BUILD=false وUSE_MOCK_DATA=false وAPI_INTERNAL_URL=http://127.0.0.1:9 وAUTONEG_BUILD_DIR=.next-release.
- PASS: TypeScript --noEmit --incremental false.
- هذه نتائج baseline الحالي Next.js 15.5.4، وليست اعتمادًا للإصدار المقترح بعد تعديل الحزم والبوابات.
- NOT_RUN: بناء Podman الجديد، اختبارات متصفح إصدار الإنتاج المقترح، نسخة احتياطية فعلية، وتجربة تراجع فعلية. لا Podman/Docker محلي متاح؛ يلزم runner معزول معتمد.
- NOT_VERIFIED: ربط Git بالصورة الحالية، webhooks، جميع طبقات التفويض والمصادقة، استجابات API الفعلية وسلامة عقودها، أتمتة خارجية غير مفحوصة.

## القرار وما تغير عن التدقيق السابق

تأكد الآن هدف الواجهة الفعلي وشبكتها وتوجيه Nginx ونسخة Next.js داخل الصورة ووجود staging وDemo، بدل الاعتماد على نسخة المصدر وحدها. ظهر خطر تخفيض Next.js، وتأكد خطر workflow النشر الشامل. ما زال تطابق المصدر مع البناء الجاري غير مثبت، ولم تُختبر الصلاحيات أو بيانات الإنتاج.

**NO-GO الآن.** الخطوة التالية المقترحة للموافقة: إعداد frontend إنتاجيًا محليًا ومحاذاة Next.js، ثم بناء/اختبار صورة منفصلة في runner معزول. أي إنشاء ملفات/حاويات على AWS أو backup/rehearsal يحتاج موافقة تتجاوز الفحص للقراءة فقط. القطع على النطاق وpush إلى main ينتظران موافقة نهائية بعد تقديم أدلة جميع البوابات. لا تغييرات على قاعدة البيانات أو خدمات Backend مطلوبة لهذا الإصدار المحدود.
