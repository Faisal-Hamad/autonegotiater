## الباك إند وقاعدة البيانات

طبّق النشر ترحيلًا إضافيًا `0002 -> 0003` لإنشاء:

1. `web_auth_sessions`: بصمات رموز جلسات الدخول ووقت الانتهاء وربط المستخدم.
2. `web_integration_records`: بيانات إعداد القوائم ومحاولات التفاوض المقيدة بالصلاحيات وإشعارات القراءة.

لم يتضمن الترحيل حذف الجداول القديمة أو استبدال سجلاتها. بقيت نماذج ORM الأساسية والعامل الخلفي وواجهات المنتجات العامة وملفات الأمان الأساسية مطابقة لبصمات الحاوية التي كانت تخدم الإنتاج. التعديلات الأساسية محصورة في config/main/workspace وإضافات التكامل.

المسارات القديمة محفوظة، لكن الوصول الخاص إليها يتطلب الآن جلسة مصادقًا عليها؛ إرسال X-Viewer-Id أو viewer_id وحده لا يمنح صلاحية. أضيفت مسارات `/auth/*` و`/integration/*`، وبقي `/integration/catalog` عامًا ببيانات عامة فقط.

لم تُنسخ قاعدة الاختبار إلى الإنتاج. لم تُنفذ fixtures أو سيناريوهات الاختبار على قاعدة الإنتاج. لم تُقرأ سجلات أعمال الإنتاج لفحص العدّ؛ ما قُرئ مباشرة بعد إذن المستخدم كان بريد Admin النشط فقط، إضافة إلى بيانات مخطط Alembic التقنية اللازمة للترحيل.

## النسخ الاحتياطية والرجوع

يحتوي نسخة إعداد Nginx الأصلية، أرشيفَي صور الواجهة والباك إند القديمين، نسخة pg_dump، وmanifest بالبصمات. فُحصت الأحجام وبصمات SHA-256 وتطابقت. نجح فحص قائمة pg_restore سابقًا؛ لم تُجرّب استعادة كاملة لقاعدة البيانات، ولم تُنسخ سجلاتها إلى staging.

الحاويتان `autoneg-nextjs` و`autoneg-fastapi` ما زالتا تعملان للرجوع. أداة `release/rollback_to_original.py` تتحقق من بصمة إعداد الإصدار ومن صورة الحاويتين الأصليتين قبل استعادة إعداد Nginx فقط. لا تستعيد قاعدة بيانات، ولا تحذف الجدولين الجديدين، ولا تمسح السجلات اللاحقة للنشر.

على الخادم وبحساب مخول:

```bash
sudo -n -u deploy python3 /home/deploy/autoneg-releases/integration-20261025-r6/rollback_to_original.py --check
# عند اتخاذ قرار الرجوع فقط:
sudo -n -u deploy python3 /home/deploy/autoneg-releases/integration-20261025-r6/rollback_to_original.py --apply
```

استُخدمت آلية استعادة التوجيه بالفعل في المحاولة الأولى؛ أعادت البصمة الأصلية الصحيحة بعد أن رفض Cloudflare فحصًا صادرًا من الخادم نفسه بـ403. لم يكن ذلك عطلًا في التطبيق؛ فحص المتصفح العام نجح. اكتمل التحويل لاحقًا بفحص HTTPS محلي يتحقق من اسم النطاق وشهادة الأصل الموثوقة الحالية، ثم تحقق مستقل بالمتصفح العام. لم يُعطّل التحقق من الشهادة ولم تُغيّر إعدادات Cloudflare.

## متطلبات التشغيل والحدود المتبقية

- حساب Admin الحالي فُعّل يدويًا؛ الحسابات القديمة الأخرى تحتاج كلمات مرور خاصة أيضًا. لا تُستخدم كلمات المرور التجريبية المنشورة للدخول الحقيقي. يمكن للمستخدم إنشاء حساب Buyer أو Seller جديد من `/register`.
- منتجات الإنتاج القديمة لا تحتوي بالضرورة معرّف كتالوج مشتركًا ومدد توصيل منظمة. يضبط البائع مدة التوصيل والمخزون والحدود الخاصة بقائمته؛ وللتنافس يضيف البائعون قوائم مرتبطة صراحة بنفس منتج الكتالوج. لا تُطابق الأسماء الجزئية ولا تُختلق عروض منافسين.
- المحرّك حتمي قائم على قواعد، وليس Gemini أو نظام AI فعليًا. لا توجد معالجة دفع أو شحن. إعدادات الإدارة غير المرتبطة بعملية مخدّمة تبقى معلوماتية ولا تمثل صلاحيات أمنية جديدة.
- لم يُدّع أن كل بيانات الإنتاج جاهزة تلقائيًا للتفاوض متعدد البائعين. عدم الأهلية بسبب غياب بيانات حقيقية حالة مقصودة.
- إعداد restart=always فُحص، لكن لم تُجرّب إعادة تشغيل EC2 أو الخدمات للتحقق من الإقلاع؛ ذلك خارج هذا الاختبار.
- لم يُعدّل GitHub Actions أو يُدفع شيء إلى GitHub. مسار النشر الآلي السابق قد يعيد بناء الإصدار القديم عند push إلى main؛ يجب تنسيق مساره مع الزميل قبل أي push لاحق. لا تشغّل reset أو force-push أو prune كجزء من هذا الإصدار.
